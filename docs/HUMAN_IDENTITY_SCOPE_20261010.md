# Identity scope at HUMAN approval and merge

Automatic proposals now retain exact tenant and canonical-type scope as immutable resolution evidence. Approval parses exact candidate UUID entries, rechecks that frozen scope against the HUMAN tenant and the current ACTIVE target under row lock, and uses the same source-identity advisory lock as resolution. An insert/update that cannot create the approved binding fails rather than falsely recording a resolved issue. No class equivalence is inferred and no historical automatic decision is rewritten. Older issues lacking explicit scope require governed re-evaluation; the service does not guess their type or overwrite their evidence. A merge requires identical canonical type and tenant; execution rechecks both objects under ordered row locks and checks the actor tenant. The existing successful merge/history and HUMAN authorization tests remain; the fixture HUMAN tenant now agrees with its actual default-tenant objects.

Seven additional PostgreSQL cases cover candidate reclassification, foreign/inactive candidates, foreign HUMAN tenant, a binding changed after proposal, missing legacy scope, cross-nature/cross-tenant merge and drift after planning. This does not certify all split, plan retrieval, concurrent-governance or end-to-end scoring surfaces. No database migration, IAM grant or target lifecycle change is performed by this patch.
